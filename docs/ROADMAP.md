**Новое:**
`hspec` — библиотека тестов. Каждый модуль `*Spec.hs` экспортирует `spec`:

```haskell
module Heos.UrlSpec (spec) where

spec = do
  describe "renderValue" $ do
```

### Этап 3 · Кодирование трёх символов

- [x] сделано

**Делаем:** `renderValue` и `decodeValue`.

HEOS кодирует **ровно три символа**:

| символ | код |
| -- | --- |
| `&` | `%26` |
| `=` | `%3D` |
| `%` | `%25` |

Больше ничего. Это **не** обычное кодирование URL: знак `+` остаётся плюсом, а не превращается в пробел.

**Ловушка:** при декодировании порядок замен важен. Если сначала заменить `%25` на `%`, а потом `%26` на `&`, то `%2526` расшифруется неправильно. Замену `%25` делай **последней** — или, надёжнее, разбирай строку за один проход слева направо, тогда порядок замен вообще не возникает.

**Проверка:** `decodeValue (renderValue "a&b=c%d")` вернуло исходное.

- [x] сделано

В ответах усилителя есть поле `message`, а в нём пары через `&`:

### Этап 6 · Оболочка ответа

- [x] сделано

**Делаем:** тип `Envelope` и разбор JSON в него.

Любой ответ усилителя выглядит так:

```json
{
  "heos":    { "command": "...", "result": "success", "message": "..." },
  "payload": ...,
  "options": [ ... ]
}
```

`payload` и `options` бывают не всегда.

**Новое:**
`aeson` — библиотека JSON. Чтобы тип умел читаться из JSON, нужен инстанс `FromJSON`. Самый простой способ — вывести автоматически:

```haskell
data HeosHeader = HeosHeader
  { command :: Text
  , result  :: Maybe HeosResult   -- у событий его нет вовсе
  , message :: Maybe Text
  } deriving stock (Show, Generic)
    deriving anyclass (FromJSON)
```

`HeosResult` — это `Success | Fail`, а не голый `Text`: опечатка `"sucess"` станет ошибкой разбора, а не тихим «не успех».

Если имена полей в JSON не совпадают с именами в Haskell — инстанс пишется руками:

```haskell
instance FromJSON Envelope where
  parseJSON = withObject "Envelope" $ \o -> do
    heos <- o .: "heos"
    payload <- o .:? "payload"     -- .:? для необязательных
    pure (Envelope heos payload)
```

Разбор: `eitherDecodeStrict :: ByteString -> Either String Envelope`.

**Проверка:** прогнать каждую фикстуру из `test/fixtures/`, все разобрались.

### Этап 10 · Найти усилитель в сети

- [x] сделано

**Делаем:** `Heos.Discovery` — найти адрес усилителя через SSDP, ничего не зная о нём заранее.

**Новое:**
SSDP — протокол обнаружения устройств поверх UDP, его же предлагает спецификация HEOS (раздел 2). Шлём один запрос `M-SEARCH` на мультикаст-адрес `239.255.255.250:1900`, его слышат все устройства в сети. Каждое подходящее отвечает отдельным пакетом прямо на наш сокет.

```http
M-SEARCH * HTTP/1.1
HOST: 239.255.255.250:1900
MAN: "ssdp:discover"
MX: 1
ST: urn:schemas-denon-com:device:ACT-Denon:1
```

- `ST` — кого ищем. Отвечать должны только устройства HEOS.
- `MX: 1` — устройство отвечает со случайной задержкой до 1 с, чтобы ответы не пришли все разом.

Три вещи про UDP, которые надо понять:

- `recvFrom` возвращает **один пакет** и адрес отправителя. Пакеты копит ядро в очереди сокета; каждый вызов забирает следующий
- у UDP **нет конца потока**. Узнать, что ответы кончились, можно только по таймауту: `timeout` вокруг `recvFrom`, `Nothing` — значит, больше никто не ответит
- таймаут — это **предел** ожидания, а не пауза: пришедший пакет отдаётся сразу

Сначала план был через `getAddrInfo` и имя `Marantz-….local`. Отказались: на Ubuntu для `.local` нужны avahi-daemon и libnss-mdns, а имя надо знать заранее. SSDP сам шлёт и сам слушает — никаких системных зависимостей.

Что осталось сделать руками:

- проверять, что в ответе есть тот же тип устройства (`heosDeviceType`), — кривые устройства отвечают на любой `ST`
- убирать дубли — ресиверы отвечают по 2–3 раза
- заменять порт отправителя на 1255 — там слушает HEOS CLI
- повторять попытку при ошибке (`retry`)

Разбор ответов — чистая функция `filterDatagrams`, вся сеть — в `discoverOnce` и `collect`. Ошибки различают диагнозы: `NoResponse` (тишина), `NoHeosDevice` (ответили, но не HEOS), `SocketFailure` (нет сети).

**Проверка:** `discover` печатает адрес усилителя: `Right (192.168.1.241:1255 :| [])`.

## Часть 3 · Живое соединение

*Самая трудная часть. Не торопись.*

### Как устроена эта часть

Каждый этап состоит из трёх шагов:

- **Эксперимент** — одна новая идея (потоки, ячейка, очередь, коробочка…) на минимальном коде, где кроме неё ничего нет. Эти эксперименты — не отступление от дела, а единственный способ понять идею прежде, чем класть её в фундамент.
- **Строим** — та же идея переезжает в `Heos.Connection` и становится частью настоящего модуля. Это и есть приложение.
- **Стенд** — `Heos.FirstTalk`. Это не часть демона, а пульт для проверки: он первым начинает пользоваться тем, что появилось в `Connection`, и с каждым этапом худеет. К концу части от него останется тридцать строк: подключиться, подписаться на события, слать команды с клавиатуры.

Что получится к концу части — целиком `Heos.Connection`, по этапам:

```haskell
data Connection                                                 -- 16; внутри: сокеты, очередь событий,
                                                                --     карта ожидающих, счётчик SEQUENCE

withConnection :: SockAddr -> (Connection -> IO a) -> IO a      -- 16, 19, 22, 24, 25
--  открыть сокет(ы), запустить чтение и heartbeat, выполнить запуск по спецификации,
--  отдать соединение в работу; по выходу — убить потоки и закрыть сокеты, что бы ни случилось

sendCommand :: Connection -> Command -> IO (Either ConnectionError Envelope)   -- 17, 18, 20, 21
--  послать команду и дождаться именно её ответа; Left — обрыв связи или таймаут

subscribe :: Connection -> IO (TChan HeosEvent)          -- 16
--  своя копия потока событий; подписчиков сколько угодно

withReconnect :: (Connection -> IO a) -> IO a                   -- 23
--  withConnection в цикле: обрыв → пауза → discover → снова
```

Реализация живёт в `Heos.Connection.Internal`, фасад `Heos.Connection` экспортирует только эти пять имён. Чистые куски (нарезка, маршрутизация входящих) покрываются тестами в `ConnectionSpec`; для потоков и сокетов тест играет роль усилителя через `socketPair` (см. этап 16).

### Этап 14 · Потоки

- [x] сделано

**Делаем:** пульт в терминале. Сейчас `readLoop` занимает главный поток навсегда — после него уже ничего не отправить. Разносим работу на два потока:

- **фоновый** — `readLoop` из этапа 13: печатает всё, что приходит из сокета, ответы и события
- **главный** — читает строки с клавиатуры (`getLine`), превращает их в `Command` и шлёт в тот же сокет

Набор команд — любой маленький, например:

| набрал | отправилось |
| -- | --- |
| `+` | `VolumeUp pid 5` |
| `-` | `VolumeDown pid 5` |
| `play` / `pause` | `SetPlayState pid Play` / `Pause` |
| `q` | выход |
| другое | подсказка |

`pid` пока можно зашить из `NOTES.md` — код временный.

Писать в сокет из одного потока и читать из другого можно: TCP-соединение двустороннее.

**Новое:**
`forkIO` запускает поток. Он дешёвый — их можно хоть тысячу.

Но у `forkIO` есть беда: если главный поток умрёт, дочерний останется висеть. И наоборот — если дочерний упадёт, никто не узнает.

Поэтому вместо него берём библиотеку `async` — стандарт для потоков в Haskell:

```haskell
import Control.Concurrent.Async (race_)

race_ (readLoop sock "") (remote sock)
-- remote закончился по `q` → фоновый поток остановлен
-- readLoop упал (сокет закрыт) → remote прерван, ошибка летит дальше
```

`race_` запускает оба действия в отдельных потоках и ждёт, кто закончит первым. Второго останавливает. Если один упал с исключением — второго тоже останавливает, а исключение выбрасывает наружу. Ни один поток не переживает вызов `race_`. Это называется структурная конкурентность: потоки не переживают блок, в котором созданы, и никто не умирает молча.

**Ловушка:** в `async` есть функции и без этой гарантии. Похожий на вид вариант

```haskell
withAsync (readLoop sock "") (\_ -> remote sock)
```

при выходе из `remote` фоновый поток остановит. Но если упадёт `readLoop`, главный поток об этом не узнает и продолжит ждать клавиатуру. Голая функция `async` ещё хуже: запущенный ею поток живёт сам по себе, как после `forkIO`. Держись `race_` и `concurrently_`.

В части 4 тот же `race_` возьмёшь из `Effectful.Concurrent.Async` — обёртка над `async` встроена в effectful.

**Строим:** в `Connection` пока ничего. Но форма `race_ (чтение) (работа)` — это скелет будущего `withConnection`: фоновый поток читает сокет, а «работа» — то, что пользователь делает с соединением. На этапе 16 этот скелет переедет в `Connection` как есть.

**Проверка:** набираешь `+` — фоновый поток печатает ответ на `volume_up` и событие `player_volume_changed`. Крутишь ручку на усилителе, пока набираешь следующую команду, — события продолжают печататься. `q` — программа выходит сама, без Ctrl+C.

### Этап 15 · Изменяемые ячейки

- [x] сделано

**Делаем:** хранить последнее полученное событие в ячейке, которую видят оба потока.

**Новое:**

- `IORef` — обычная изменяемая ячейка. `newIORef`, `readIORef`, `writeIORef`.
- `TVar` — то же самое, но для транзакций. Работа с ним оборачивается в `atomically`.

```haskell
import Control.Concurrent.STM

v <- newTVarIO (0 :: Int)
atomically $ writeTVar v 42
x <- atomically $ readTVar v
```

Зачем `TVar`, если есть `IORef`: несколько изменений можно объединить в **одну** атомарную операцию. Либо всё случилось, либо ничего. Это называется STM — транзакционная память. Внутри `atomically` нельзя делать ввод-вывод, только работать с ячейками, и именно поэтому оно надёжно.

Правило выбора, которое здесь выяснилось:

| что | когда |
| -- | --- |
| аргумент рекурсии | состояние одного цикла в одном потоке (`buffer` в `readLoop`, `seqNo` в `remote`) |
| `IORef` | изменяемое состояние одного потока, когда аргументом передать неудобно |
| `TVar` | состояние, общее для нескольких потоков |

**Строим:** в `Connection` пока ничего. `volumeRef` — прообраз кэша из этапа 30: там такая же ячейка, только с полной картиной (плееры, громкость, что играет), и обновляет её тот же поток чтения. Из `FirstTalk` ячейка потом просто исчезнет.

**Проверка:** один поток пишет, другой читает, значения не теряются.

### Этап 16 · Очередь событий

- [x] сделано

**Эксперимент:** читающий поток больше не печатает и не разбирает события сам — он кладёт каждое в очередь. Подписчиков двое, и у каждого своя копия очереди: один печатает всё подряд, другой следит только за громкостью и обновляет `volumeRef`. Потоков становится три:

```haskell
race_ (concurrently_ reader printer) remote
```

**Новое:**

- `TQueue` — очередь. `writeTQueue`, `readTQueue`. Чтение из пустой очереди **ждёт**, пока кто-нибудь не напишет.
- `TChan` + `dupTChan` — то же, но нескольким подписчикам сразу, каждый получит свою копию.

Для событий бери `TChan`: подписчиков может быть несколько.

**Ловушка:** обычный `newTChan` копит сообщения, даже если читателей нет, — утечка памяти на долгоживущем демоне. Создавай канал через `newBroadcastTChanIO`: в него можно только писать, а читают через копии от `dupTChan`. Нет подписчиков — события просто пропадают, как и должно быть.

**Строим:** первый настоящий код в `Heos.Connection.Internal`:

```haskell
data Connection = Connection
  { sock   :: Socket
  , events :: TChan HeosEvent      -- broadcast; читать только через subscribe
  }

withConnection :: SockAddr -> (Connection -> IO a) -> IO a
-- bracket: открыть сокет / закрыть; внутри — race (reader conn) (act conn)

reader :: Connection -> IO Void           -- readLoop из этапа 13: нарезать, разобрать, положить в events
subscribe :: Connection -> IO (TChan HeosEvent)   -- atomically (dupTChan conn.events)
```

`reader` никогда не возвращается, поэтому его тип `IO Void`. Тогда у `race` результат `Either Void a`, и левую ветку можно закрыть через `absurd` из `Data.Void`: компилятор сам знает, что чтение не может «успешно закончиться».

Временно добавь `sendRaw :: Connection -> ByteString -> IO ()`, чтобы стенд мог слать команды. На этапе 17 она исчезнет.

**Шов для тестов:** раздели `withConnection` на две функции — `withConnection` только открывает сокет по адресу, а всю работу делает `runConnection :: Socket -> (Connection -> IO a) -> IO a`. Тогда в тестах `socketPair` даёт пару соединённых сокетов без сети: один отдаём `runConnection`, во второй тест пишет строки от имени усилителя. Так проверяется вся часть 3 — без аппарата.

**Стенд:** `FirstTalk` теряет свой сокет, `bracket` и `readLoop`:

```haskell
withConnection addr $ \conn -> do
  ch <- subscribe conn
  race_ (printer ch) (remote conn 0)
```

**Проверка:** событие, положенное одним потоком, забирается другим. Пульт работает как раньше, но весь код сокета теперь в `Connection`. Тест: через `socketPair` подсунуть `reader` две строки, подписчик получает оба события в том же порядке.

### Этап 17 · Ждём ответа

- [x] сделано

**Эксперимент:** послать команду и дождаться именно её ответа — а не печатать всё подряд и выискивать свой глазами.

**Новое:**
`TMVar` — ячейка, которая может быть **пустой**. Чтение из пустой блокируется, пока туда не положат.

```haskell
box <- newEmptyTMVarIO       -- создали пустую
-- где-то в другом потоке:
atomically $ putTMVar box ответ
-- здесь:
ответ <- atomically $ takeTMVar box   -- ждём, пока положат
```

Это ровно то, что нужно: отправитель создаёт пустую коробочку и садится её ждать, читающий поток кладёт туда ответ.

**Строим:** в `Connection` появляется место для одной коробочки и первая версия главной функции:

```haskell
pending :: TVar (Maybe (TMVar Envelope))   -- новое поле Connection

sendCommand :: Connection -> Command -> IO Envelope
-- создать коробочку → положить в pending → отправить → ждать коробочку
```

`reader` теперь сортирует входящее по `classifyEnvelope`:

- `IncomingEvent` → в `events`, как на этапе 16
- `IncomingResponse` → в коробочку из `pending`
- `IncomingPending` («command under process») → **ничего не делать**. Это ловушка этапа 7: если положить его в коробочку, отправитель получит «ответ» без результата, а настоящий придёт позже и останется без хозяина

Ответ с `result: fail` — тоже ответ: он кладётся в коробочку как есть. Различать `Succeeded`/`Failed` будет уровень ниже (этап 26).

Пока в полёте может быть только одна команда — коробочка одна. Этап 18 это исправит.

**Стенд:** `sendRaw` удаляется. `+` в пульте делает `sendCommand conn (VolumeUp pid 1) >>= print` и печатает **только свой ответ**; `printer` печатает только события. `GetPlayers` и `RegisterForChangeEvents` при старте тоже идут через `sendCommand`.

**Проверка:** `sendCommand conn GetPlayers` возвращает результат, а не зависает. Тест через `socketPair`: усилитель-подделка отвечает с задержкой, `sendCommand` ждёт и получает именно этот ответ; «command under process» перед ответом ничего не ломает.

### Этап 18 · Кто чего ждёт

- [x] сделано

**Эксперимент:** несколько команд в полёте одновременно, и каждый ответ находит своего отправителя.

**Строим:** одна коробочка превращается в карту, а номер выдаёт единый счётчик:

```haskell
pending  :: TVar (Map Int (TMVar Envelope))   -- номер запроса → коробочка
nextSeq  :: TVar Int                          -- один на соединение
sendLock :: MVar ()                           -- см. ловушку ниже
```

Порядок в `sendCommand`:

1. взять следующий номер — `atomically (stateTVar nextSeq (\n -> (n, n + 1)))`: прочитать и увеличить одной транзакцией, иначе два потока возьмут один номер
2. создать пустую коробочку, положить в карту под этим номером
3. послать команду с `SEQUENCE=<номер>`
4. ждать коробочку
5. **убрать из карты** — обязательно, при любом исходе (этап 19)

Выбор коробочки вынеси в чистую функцию и покрой тестами — это легко сделать без сокета:

```haskell
findBox :: Maybe Text -> Map Int box -> Maybe box
-- по message ответа и карте ожидающих: чья это коробочка, если вообще чья-то
```

Внутри — разбор `SEQUENCE` из `message` и правила из ловушки ниже. `reader` после неё делает одно: нашлась коробочка — положить, нет — записать в лог и выбросить. Сортировку «событие / ответ / command under process» оставь в `reader` обычным `case` по `IncomingEnvelope`: там по строке на ветку, отдельный тип ради этого — удлинение ради ничего.

**Ловушка (проверено на аппарате, см. `NOTES.md`):** `SEQUENCE` возвращается только если у команды есть **свои** аргументы — аппарат копирует в `message` аргументы запроса, и номер едет вместе с ними. У `get_players` аргументов нет, и номер теряется. Поэтому:

- ответ **с** номером → коробочка с этим номером
- ответ **без** номера → единственная команда в полёте. Чтобы она действительно была единственной, отправка идёт под замком `sendLock` (`withMVar`): одна команда за раз
- номер есть, а коробочки под ним нет → это **опоздавший** ответ на команду, которая уже не ждёт (этап 21). Записать в лог и выбросить — ни в коем случае не отдавать следующему отправителю

С замком карта почти всегда содержит одну запись. Она всё равно нужна: именно она отличает свой ответ от опоздавшего, а если выяснится, что все нужные команды возвращают номер, замок можно будет снять, не меняя остального.

**Стенд:** без изменений — пульт и так шлёт по одной команде. Разве что убрать счётчик из `remote`: номер теперь выдаёт `Connection`.

**Проверка:** послать три команды подряд, получить три правильных ответа, не перепутав. Тест через `socketPair`: подделка отвечает на две команды с `SEQUENCE` в обратном порядке — каждый `sendCommand` получает свой ответ; ответ с чужим номером никому не достаётся.

### Этап 20 · Когда всё сломалось

- [x] сделано

**Эксперимент:** выдернуть усилитель из сети посреди работы и посмотреть, что станет с программой.

Это самое важное место во всём проекте. Четыре из пяти известных багов живут здесь.

**Ловушка, которая уже сидит в коде:** когда усилитель закрывает соединение, `recv` в `network` 3.x не бросает исключение, а возвращает **пустую строку**. Текущий `readLoop` тогда уходит в бесконечный цикл без ожидания: пустая строка → ничего не нарезалось → снова `recv` → снова пустая строка. Программа не падает и не выходит, а молча съедает ядро процессора. Это и есть первая настоящая поломка — найди её руками до того, как чинить.

**Строим:**

```haskell
data ConnectionError = ConnectionLost | Timeout   -- Timeout появится на этапе 21

sendCommand :: Connection -> Command -> IO (Either ConnectionError Envelope)
```

- `reader`: пустой `recv` — это конец потока; бросить исключение, а не продолжать
- `reader` при любом завершении (`finally`): пройти по всей карте, положить в каждую коробочку `Left ConnectionLost`, карту очистить. Коробочки хранят `Either ConnectionError Envelope`
- ошибка при отправке в `sendCommand` — тоже `Left ConnectionLost`

**Стенд:** без изменений — он нужен для проверки руками.

**Обязательная проверка руками:**

1. послать команду
2. выдернуть усилитель из сети (или выключить Wi-Fi на маке)
3. программа должна **выдать ошибку**, а не висеть вечно и не крутиться вхолостую

Если висит или греет процессор — этап не сделан. Тест: подделка закрывает свой конец `socketPair` — `sendCommand` возвращает `Left ConnectionLost`, `withConnection` завершается.

### Этап 22 · Heartbeat

- [x] сделано

**Эксперимент:** оставить соединение без дела на час.

Простаивающее соединение усилитель рано или поздно закроет.

```haskell
heartbeat :: Connection -> IO Void
heartbeat conn = forever $ do
  threadDelay (30 * 1000000)   -- 30 секунд
  sendCommand conn HeartBeat
```

**Новое:** потоков теперь три: чтение, heartbeat и основная работа. `race_` берёт два действия; `concurrently_` запускает два действия и ждёт **оба**, а если одно упало — останавливает второе и выбрасывает ошибку. Чтение и heartbeat бесконечны, поэтому `concurrently_` из них закончится только ошибкой:

```haskell
race (concurrently_ (reader conn) (heartbeat conn)) (act conn)
```

**Строим:** эта строка — новая середина `withConnection`. `heartbeat` — обычный пользователь `sendCommand`: идёт под тем же замком и через ту же карту, никакого особого пути. Если `HeartBeat` вернул `Left`, соединение мертво — пусть `heartbeat` бросит исключение, и `withConnection` завершится ошибкой, а не будет молча ждать.

**Стенд:** без изменений.

**Проверка:** оставить демон на час, соединение живо. Тест: с интервалом в миллисекунды подделка видит `system/heart_beat` в потоке команд.

### Этап 23 · Переподключение

- [x] сделано

**Эксперимент:** выключить аппарат, подождать, включить.

**Строим:** `withConnection` остаётся честной функцией «одно соединение от открытия до закрытия». Поверх неё — повтор:

```haskell
withReconnect :: (Connection -> IO a) -> IO a
```

Одна попытка — это `discover`, затем `withConnection addr act`. Адрес ищется заново перед каждой попыткой: после перезагрузки роутера DHCP мог выдать усилителю другой IP, а полторы секунды на поиск после обрыва не жалко. Попытка заканчивается только исключением: `DiscoveryError` (аппарат не нашли, у типа появляется `instance Exception`), `ConnectionError` (обрыв или молчание) или `IOException` (`connect` к выключенному аппарату, `recv` после выдернутой вилки). На любое из трёх — пауза и новая попытка.

Повтор делает `recovering` из пакета `retry`: ему отдаются политика пауз, список обработчиков (`Handler` из `Control.Monad.Catch`, пакет `exceptions`) и сама попытка. Пауза растёт: 1с, 2с, 4с, 8с, дальше не больше минуты: `capDelay 60с (exponentialBackoff 1с)`. Лимита попыток нет: усилитель выключили на ночь — демон ждёт утра.

Не долбить усилитель раз в секунду, когда его выключили из розетки.

Простой вариант: вместе с соединением перезапускается и `act`. Для пульта и для этапа 24 это правильно — запуск по спецификации и должен повторяться при каждом подключении. В части 6 выяснится, что HTTP-сервер при обрыве перезапускать нельзя; тогда соединение спрячется за ячейку, а `sendCommand` без соединения будет сразу отвечать `Left ConnectionLost`. Пока не нужно.

**Стенд:** `withConnection` в `FirstTalk` меняется на `withReconnect`. Больше ничего.

**Проверка:** выключить аппарат, подождать минуту, включить — демон сам восстановился.

### Этап 24 · Правильный запуск

- [ ] сделано

**Строим:** `initialize :: Connection -> IO ()` — последовательность при подключении, как велит производитель:

1. `system/register_for_change_events?enable=off` — выключить события

**Стенд:** из `FirstTalk` исчезают `GetPlayers` и `RegisterForChangeEvents` при старте — это делает `initialize`.

**Проверка:** демон стартует и печатает полное состояние системы. Тест: подделка видит команды запуска именно в этом порядке.

### Этап 35 · MCP-сервер

- [ ] сделано

**Делаем:** подключаем `mcp-server`, транспорт **HTTP** (не stdio — иначе демон будет перезапускаться на каждую сессию и вся идея пропадёт).

Инструменты. Чем меньше, тем лучше — агенту проще выбрать:

- `heos_status` — что играет, без аргументов, из кэша
- `heos_play_music` — найти и поставить: `query`, `kind`, `mode`
- `heos_transport` — `play` / `pause` / `next` / `prev`
- `heos_volume` — уровень, прибавить, приглушить
- `heos_search` — только найти, не ставить

Правила:

- аргументы плоские, без вложенности
- ответы короткие: агент платит токенами за каждый символ
- ошибки по-человечески: «усилитель не отвечает, возможно выключен», а не `ECONNREFUSED`

**Проверка:** инструменты видны, вызываются, музыка играет.
